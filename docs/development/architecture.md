# Architecture Status

The fixed integration boundary is the unmodified official bw CLI. Decisions and their status are in the [decision index](../decisions/README.md).

**Everything on this page is planned, except where a status says otherwise.** The code that exists is the Go module with the packages `internal/capture` and `internal/verify` from the archived change `capture-verification`, the packages `internal/manifest`, `internal/archive` and `internal/publish` and the command `cmd/bw-takeout` with its single subcommand `verify` from the change `archive-generation`, and the packages `internal/bwcli`, `internal/profile` and `internal/vaultid` with the development tool `internal/tools/loginprobe` from the change `bw-process-adapter`. The change `archived-item-list` extended `internal/capture`, `internal/verify` and `internal/archive` to a second item list. The change `capture-collection` added the package `internal/collect` and extended `internal/capture` and `internal/verify` by decryption error counts and attachment file names. The change `interactive-backup-run` added the packages `internal/run`, `internal/report`, `internal/offline` and `internal/printable` and the subcommand `backup`. The change `memory-hardening` added the package `internal/crashdump`. The change `vaultwarden-test-setup` added the test package `internal/e2e` behind the build tag `vaultwarden`, which no product code imports, and the workflow `vaultwarden.yml`. The change `organization-export` extended `internal/bwcli`, `internal/collect`, `internal/capture`, `internal/verify`, `internal/manifest`, `internal/archive`, `internal/offline`, `internal/run`, `internal/report` and `cmd/bw-takeout` to chosen organizations, and `internal/e2e` by an organization scenario. The component model and the roadmap come from the explore session of 13 November 2026 and may change with each later change.

## Planned flow

Checks before the first `bw` process → profile, version, server and interactive login → sync and inventory → JSON exports and individual attachment downloads → verification result → encrypted archive → published generation → logout and removal of the profile. `bw-takeout backup` runs this flow in `run` and reports it through `report`. Every step exists and is tested against a fake `bw` and with synthetic captures. The [manual backup exercise](testing.md#backup-exercise-of-18-november-2026) ran the flow against Vaultwarden on Linux and macOS on 18 November 2026.

Collecting a capture exists in two phases, tested against an in-memory vault and the fake `bw`:

- **Snapshot**, before the target directory is touched: one forced sync, the freshness check, the role check of the chosen organizations, the four documents and the two organization exports of each chosen organization with their decryption error counts, the source for the manifest and the plan of attachment downloads.
- **Attachments**, inside the write function of the publishing step: one download at a time, each handed to the archive writer and then cleared, with one download result per planned attachment.

`run` calls the snapshot before it touches the target, the attachments inside the write function of the publishing step, and `Snapshot.Wipe` as soon as the capture is parsed. Teardown follows on every path. Personal and organization views are handled separately: the personal exports and the item lists come from the local snapshot, and the organization exports of the chosen organizations from separate reads of the server after it. Their checks run per organization inside the one verdict, and items of organizations that are not chosen are outside the scope ([ADR 0008](../decisions/0008-organization-export.md)).

## Rules

1. Only one component knows `bw`. Everything else works against an interface and is testable with a fake.
2. Verification is a pure function over a captured data model.
3. Plaintext exists only in process memory and inside the encryption stream. This program writes none of it to a file, but the operating system can still put process memory on disk: swap, hibernation and core dumps (see the [security page](../user/security.md#swap-hibernation-and-core-dumps)). On Linux and macOS the core file size limit of the run is zero before the first `bw` process starts and is inherited by every `bw` process, and on Linux the run process is not dumpable (`crashdump`). Windows is not limited.
4. Only one component touches the target directory, and it only creates new names.

## Components

| Component | Responsibility | Status |
|---|---|---|
| `bwcli` | Start `bw`, build the child environment from an allowlist, report the version and the SHA-256 of the executable without judging them ([ADR 0007](../decisions/0007-bw-versions.md)), pass the session key to child processes only, collect stdout in memory, count decryption error lines, classify failures without CLI text, run the interactive login | implemented, tested against a fake `bw` in the dev container and in CI on Linux, macOS and Windows, login exercised by hand against Vaultwarden on Linux and macOS |
| `profile` | Own CLI data directory per run, list leftovers of earlier runs without removing them, teardown also when the logout fails | implemented, tested in the dev container and in CI on Linux, macOS and Windows. A fresh profile per run is a maintainer decision for the prototype (15 November 2026) |
| `capture` | Capture model and parsers for four documents, with the default and the archived item list as separate documents, decryption error counts per document and download, attachment file names for the manifest, and the one function that decides which attachments are expected | implemented |
| `collect` | Collect one capture from a logged-in client in two phases: forced sync, freshness check, documents, download plan, then attachment downloads with retries and classification of failures. Works against an interface that `bwcli.Client` satisfies | implemented, tested against an in-memory vault and the fake `bw` |
| `verify` | Turn a capture into a verdict with reasons per ID, over the combined listing of both item lists, including decryption error lines | implemented |
| `manifest` | Format version, creation time, source, versions, entry sizes and hashes, embedded verification result | implemented |
| `archive` | Write and read the age-encrypted tar stream with four captured documents, recovery instructions, recipient and identity parsing | implemented |
| `publish` | Create a new partial generation directory exclusively, flush, publish by verdict without replacing, list leftovers | implemented, tested on Linux only |
| `crashdump` | Set the soft and the hard core file size limit of the process to zero on Linux and macOS, inherited by every `bw` process, and mark the process as not dumpable on Linux, each confirmed by reading it back | implemented for Linux and macOS. Windows reports "not limited" and changes nothing. Tested in the dev container on Linux and in CI on Linux, macOS and Windows, with the real system calls on Linux and macOS |
| `run` | Checks before the first `bw` process, order of phases, teardown with a bounded logout, interrupts, one outcome per run. Works against an injected profile, terminal, clock, signals and publisher | implemented, tested against the fake `bw` |
| `report` | Progress, final report with redaction and every finding, exit status of a backup | implemented, tested with synthetic outcomes and through `run` |
| `offline` | The `verify` command. Its dependency list holds no network package, no `os/exec` and none of `verify`, `bwcli`, `collect` and `run`, which a test checks | implemented, moved from `cmd/bw-takeout` |
| `printable` | Replacement of characters that are not printable, shared by `offline` and `report` | implemented |

## Roadmap

1. `capture-verification`: verdict rules over a captured inventory. Done, archived on 14 November 2026. The agreed behavior is in `openspec/specs/capture-verification/`.
2. `archive-generation`: container, encryption, manifest, exclusive publishing and an offline verify command. Done, archived on 14 November 2026. The agreed behavior is in `openspec/specs/backup-archive/`, `openspec/specs/generation-publishing/` and `openspec/specs/offline-verification/`.
3. `bw-process-adapter`: `bwcli` and `profile` against a fake `bw`, unauthenticated tests with the real binary and a manual login exercise against Vaultwarden on Linux and macOS. Done, archived on 15 November 2026. The agreed behavior is in `openspec/specs/bw-invocation/` and `openspec/specs/bw-profile/`. Results are in the [code notes](../research/bw-cli-code-notes-2026-11-15.md) and the [login exercise](../research/login-exercise-2026-11-15.md).
4. The former item `interactive-backup-run` was split into four changes in the explore session of 16 November 2026. Together they complete the first prototype. B builds on the model of A. The explore session of 18 November 2026 settled the questions of C and moved memory hardening out of it into E, and the explore session of 19 November 2026 settled the scope of E. D is not created yet.
   - **A. `archived-item-list`**: the capture holds the default and the archived item list as two documents, the verification treats them as one listing and reports an archive filter that did not apply, and the archive stores the fourth document `documents/items.archived.json`. Done, archived on 16 November 2026. The agreed behavior is in `openspec/specs/capture-verification/`, `openspec/specs/backup-archive/` and `openspec/specs/offline-verification/`. This takes the obligation that the capture must include `list items --archived`, because the default list leaves archived items out while both exports keep them ([live probe](../research/vaultwarden-live-probe-2026-11-14.md), added case "archived item"; [code notes of 16 November 2026](../research/bw-cli-code-notes-2026-11-16.md)).
   - **B. `capture-collection`**: collect a capture through `bwcli` in two phases, snapshot and attachments, against an interface that `bwcli.Client` satisfies. Tested against an in-memory vault and the fake `bw`. Done, archived on 18 November 2026. The agreed behavior is in `openspec/specs/capture-collection/` and `openspec/specs/capture-verification/`. The decisions of 17 November 2026:
     - Freshness rule: the run forces one sync and requires `bw status` to report an unlocked vault and a `lastSync` at or after the start of that sync, compared at millisecond precision. A failed or stale sync ends the run without a generation. It does not lower the verdict.
     - No comparison of the inventory before and after the capture. `list`, `export` and `get` start no sync of their own, so the one forced sync fixes the snapshot for every later command ([code notes of 17 November 2026](../research/bw-cli-code-notes-2026-11-17.md), code reading only).
     - Premium failure: a failed download without a retry, never more lenient than any other failed download. An account with lapsed premium and personal attachments gets no generation ([limitations](../user/limitations.md)).
     - Download failures: a timeout or a non-zero exit code is tried up to three times, with waits of 2 and 5 seconds. Output beyond the output limit of 1 GiB is a failed download without a retry (review of 18 November 2026). Not logged in, locked, cancelled, failure to start, an unused profile and a stray file end the run. The remaining failures map to the three download error classes.
     - Decryption error lines: lines on any of the four documents make the verdict at least unverified, lines on a successful download give a warning. [ADR 0004](../decisions/0004-completeness-verdict.md) stays proposed and was updated in place.
     - Default time limit of one attachment download: 5 minutes instead of 30.
     - Plaintext in memory: one attachment at a time, cleared after the archive writer took it, a `Wipe` method for the four documents, and an output buffer in `bwcli` that clears what it leaves behind when it grows. No step writes a file. Decoded JSON trees, file names and other strings are not cleared and stay until the garbage collector frees them. This residual risk went to the memory hardening of C and then of E, which left it documented on the [security page](../user/security.md#swap-hibernation-and-core-dumps).
   - **C. `interactive-backup-run`**: the `backup` command, order of phases, the login, teardown and logout on abort, report and exit codes, user documentation. Tested against the fake `bw`, and by hand against Vaultwarden on Linux and macOS in the [backup exercise of 18 November 2026](testing.md#backup-exercise-of-18-november-2026). Done, archived on 18 November 2026. The agreed behavior is in `openspec/specs/backup-run/`. The decisions of 18 November 2026:
     - Inputs are flags only: `--server`, `--target` and `--recipients-file` are required, `--bw` and `--ca` optional. `--server` is required so that a fresh profile never falls back to the default cloud server unnoticed. The recipients file has the form of the identity file. There is no configuration file yet.
     - Checks before the first `bw` process: the target is an existing directory, the recipients file yields a recipient, `bw` resolves to a regular file and a given CA file is readable. A mistake costs no two-step code.
     - Order: the snapshot before the target is touched, the attachments, the verification and the archive inside the publishing step, and `Snapshot.Wipe` as soon as the capture is parsed. Done.
     - The report names attachments by ID, a failure by its phase, `bw` operation and class, and the server from the flags when `bw status` reports none. It lists every finding and warning, also for a failed verdict, for which it is the only record. Done.
     - Teardown: a logout after every login attempt, also a failed one, with a limit of 10 seconds, then the removal of the profile on every path. Done.
     - Interrupts: the first ends the run and aborts a generation that is not committed, a second skips the logout. On Unix SIGTERM and SIGHUP count as interrupts. The run decides from its own record that it was interrupted.
     - Exit statuses 0, 3, 4, 1 and 2. Status 4 marks a published generation whose logout did not succeed or whose profile was not removed.
     - One binary: `verify` moved into `internal/offline`, and the dependency test checks that package instead of the binary.
     - Swap, hibernation and core dumps are documented as residual risk in [security](../user/security.md#swap-hibernation-and-core-dumps), with the advice to use encrypted swap or an encrypted disk, and rule 3 above is corrected. Done.
     - The next live run includes an archived item with an attachment. Done: the backup exercise of 18 November 2026 found the attachment of the archived item in every generation.
   - **D. FAT and exFAT run**: the run of `publish` on a FAT or exFAT target that was deferred from `archive-generation`, see [testing](testing.md). Independent of `bw`.
   - **E. Memory hardening**, change `memory-hardening`: limit crash dumps before the first `bw` process. Done, archived on 19 November 2026. The agreed behavior is in `openspec/specs/backup-run/`. The decisions of 19 November 2026:
     - On Linux and macOS the run sets the soft and the hard core file size limit of its process to zero and reads them back. Every `bw` process inherits both. On Linux the run process is also marked as not dumpable, which does not reach `bw`.
     - Fail closed: on Linux and macOS a run whose limit or mark cannot be set, or does not read back as set, ends in the checks with no generation, before a profile is created and before `bw` starts.
     - A debugger can no longer attach to a running `bw-takeout` on Linux. Accepted.
     - Windows continues unlimited and says so in the report. Its way is a follow-up in item 5.
     - The [security page](../user/security.md#swap-hibernation-and-core-dumps) states what is limited per platform and that a crash handler named by a piping `core_pattern` decides on its own. [ADR 0006](../decisions/0006-secret-boundary.md) stays proposed and was updated in place.
5. Follow-ups recorded by `bw-process-adapter`, `capture-collection`, `interactive-backup-run`, `vaultwarden-test-setup` and `vaultwarden-totp-login`, not yet ordered:
   - An automated Vaultwarden test setup, including account creation without a person. Done with the change `vaultwarden-test-setup`, archived on 21 November 2026 after a passing run of `vaultwarden.yml` on Linux amd64. It has no spec delta: the suite `internal/e2e` behind the build tag `vaultwarden` with an intact and a tampered-passkey scenario, and the workflow `vaultwarden.yml`, started by hand. See [Vaultwarden tests](testing.md#vaultwarden-tests) and the [spike of 21 November 2026](../research/vaultwarden-registration-spike-2026-11-21.md).
   - Report a logout after a refused login in a way that does not read as a second failure, a change of the `backup-run` report. In both login failure scenarios of `vaultwarden-totp-login`, the report shows `Logout:      failed (exit)` after a login that the server refused, although nothing was logged in, so it tells the user about a second error that did not happen. This changes the `backup-run` spec and is not part of that change.
   - The second change on the automated Vaultwarden setup, `vaultwarden-totp-login`: an account with two-step login (TOTP) in the intact scenario, and the login failures with a wrong master password and a wrong two-step code. Done with the change `vaultwarden-totp-login`. It has no spec delta. See [Vaultwarden tests](testing.md#vaultwarden-tests).
   - A third change on the automated Vaultwarden setup: a deleted or corrupted attachment file on the server and an interrupt during a live backup. Blob-format items, a lapsed premium and the archive filter cannot be produced on Vaultwarden 1.37.4: `bw` 2026.10.1 wrote legacy items against it, and the server reports premium for every user. They need Bitwarden Cloud or another server.
   - A small change that reports export fields unknown to this project at run time.
   - Reusing one profile across runs in a logged-out state, so that the server keeps one device entry. To be looked at before a first release.
   - Publishing failed captures under a marker, raised by `capture-collection` for accounts whose premium lapsed. A later explore session may take it up.
   - Comparing passkey counters with an earlier generation. Reading an earlier generation needs an identity, which ADR 0003 keeps off the backing-up system, so this fits an offline comparison of two generations.
   - A machine-readable report such as `--json`, and with it the question whether progress moves to standard error.
   - Progress per attachment while the downloads run. `collect` returns the download results only at the end, so the report prints the attachment lines after the downloads (review of 18 November 2026, finding C3).
   - An exit status that tells an aborted run from a failed verdict. Both give 1 now.
   - Windows experiment, raised by `memory-hardening`: crash dumps through Windows Error Reporting, a job object for the run, stopping the whole process tree, and `bw.cmd`. `npm` installs `bw` as a script there. Whether starting it behaves like the single-file `bw.exe` for arguments, the environment and stopping is untested.
6. Later: platform hardening, configuration and multiple accounts (including the attachment time limit and the number of download attempts that `capture-collection` fixed, and the logout limit that `interactive-backup-run` fixed), release, then batch operation and a KDBX derivative. Organizations were taken out of this item and moved ahead in the explore session of 21 November 2026: done with the change `organization-export`, backup of chosen organizations through the organization export with an owner or admin role, on Vaultwarden 1.37.4 only. Its untested cases, Bitwarden Cloud and custom roles with the export permission, are documented in the [limitations](../user/limitations.md#organizations). Batch operation needs login data taken from another vault instead of the terminal. Platform hardening starts with locking memory: it does not reach the `bw` processes, common limits are smaller than a vault with attachments, and Go gives little control over copies on the heap, so an experiment per platform comes first.

Not planned at all: capturing the trash, which is a [non-goal](../product/non-goals.md) of the product. Both personal exports and both item lists leave deleted items out, so items in the trash are not backed up (maintainer decision, 16 November 2026, see [limitations](../user/limitations.md)).

The live probe against a disposable Vaultwarden instance ran outside this sequence on 13 and 14 November 2026. Its results are in the [live probe report](../research/vaultwarden-live-probe-2026-11-14.md).

## Expected decisions

The change `capture-verification` added the proposed [ADR 0004](../decisions/0004-completeness-verdict.md) on the completeness verdict and its scope claim, and the change `archive-generation` the proposed [ADR 0005](../decisions/0005-archive-format.md) on archive format and generation layout. The change `bw-process-adapter` added the proposed [ADR 0006](../decisions/0006-secret-boundary.md) on the secret boundary around the `bw` process and the proposed [ADR 0007](../decisions/0007-bw-versions.md) on the handling of `bw` versions. The ADRs on Go and age stay proposed until their open points are tested. ADR 0002 on Go now has evidence for Linux and macOS, and Windows is open. The [decision index](../decisions/README.md) lists what exists.
