# age as Archive Encryption

Status: proposed

## Context

A backup must be readable offline with a separately stored key, independently of the Bitwarden account and of this project's software. The account-bound encrypted export can only be read with the account key, so it does not meet this requirement. age provides an existing, specified format with a reference implementation in Go and independent implementations, and it can be used offline. Compared to account-bound encryption, independent readability can be tested directly.

## Decision

Archives are encrypted with age, through the library `filippo.io/age` in the version that `go.mod` pins. It is updated like every other module ([integrations](../development/integrations.md)). The decision was made with version 1.2.1; on 17 November 2026 the library moved to 1.3.2 without a change of the recipient model below or of the archive format.

**Recipient model.** An archive is encrypted to one or more native X25519 recipient keys. Writing needs only the public keys, so the backing-up system holds no secret that opens an archive. Any other recipient form is refused. A passphrase mode may follow later. The age format allows a passphrase only as the sole recipient of a file, so a generation will be encrypted either to a passphrase or to recipient keys.

**Key loss.** Each matching identity alone opens an archive. Users protect against losing one key by encrypting to two or more recipients, for example one identity kept on paper or offline media and one on a second device.

**Offline recovery.** Recovery with the standard age and tar commands, without this project, is tested in the dev container, and `bw-takeout verify` checks a generation offline with an identity file. The archive format is recorded in [ADR 0005](0005-archive-format.md).

## Alternatives

- **Account-bound encrypted export only.** Readable only with the account key and the Bitwarden software, so offline and independent recovery is not possible.
- **Adopting the hybrid post-quantum recipients of age 1.3.** Deferred so that the tool version does not change together with a feature. The library is at 1.3.2, but the project parses only X25519 recipients and identities, so a hybrid recipient is refused. Adopting it later is additive, because the archive format stays the same.

## Consequences

- The user must keep an identity and an age implementation outside the archive. The [recovery page](../user/recovery.md) names what to keep.
- The backing-up side cannot test decryption after writing. The offline verification with the identity is a separate act.
- The library and the age CLI used by the recovery test are pinned separately and may differ in version, which tests that an archive opens with another age version ([integrations](../development/integrations.md)).
- A library update that adds a recipient or identity type does not change what the project accepts, because only X25519 recipients and identities are parsed.

## Open Points

- **No sender authentication.** Recipient encryption does not prove who wrote an archive. Anyone who knows a recipient key can create an archive that verifies. Offline verification proves consistency and readability, not origin.
- **Hybrid post-quantum recipients.** age 1.3 added them, and they are not evaluated here. The archives hold passkey private keys, so harvest-now-decrypt-later matters for archives stored outside the user's control.

Acceptance needs an explicit project decision on these two points.
