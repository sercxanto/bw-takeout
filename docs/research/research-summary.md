# Research Overview

The following evidence levels refer to the included investigations of 31 October 2026. The bootstrap check does not repeat their experiments. The original reports are in German.

| Subject | Finding and scope |
|---|---|
| Passkey export | In the successful synthetic export path of the examined CLI version 2026.10.1, 13 native fields including keyValue and counter are confirmed. This does not imply that every backed-up passkey can be used to log in successfully. |
| Attachments | In the tested ZIP service path, name collisions and skipped download errors were reproduced. Plan individual downloads per item ID and attachment ID, and record results and errors per ID. |
| Silent omission | SDK/export service experiment with corrupt key material: an item or its credentials can be missing. Code analysis shows shared decrypted views for list and export. Matching counts and the exit code are not sufficient proof of completeness. |
| Second inventory | In the personal legacy test, account-bound encrypted_json showed two expected credentials despite an empty plaintext inventory. For the modeled blob, only the outer ID was visible. Equal counts do not prove equal content. |
| Freshness and permissions | Stale sync was modeled. Actual server completeness, organization permissions, access to organization attachments and Vaultwarden compatibility need separate live tests. Organization permissions and attachments were later observed on Vaultwarden 1.37.4, see the [organization spike](organization-export-spike-2026-11-21.md); Bitwarden Cloud remains untested. |
| KDBX | The converter audit describes field losses and robustness problems. A later derivative needs its own loss and recovery tests. |
| Vaultwarden live probe | [Run of 14 November 2026](vaultwarden-live-probe-2026-11-14.md) with the real bw 2026.10.1 process against Vaultwarden 1.37.4, personal legacy items only. With foreign ciphertext in one keyValue, JSON export and list exited with 0 and showed 0 of 2 passkeys, while encrypted_json showed 2. Attachments with the same name were byte-exact per ID. Archived items are missing from the default list but present in both exports. Bitwarden Cloud, blob items and organizations were not tested. |
| bw process boundary | [Code notes of 15 November 2026](bw-cli-code-notes-2026-11-15.md) on the 2026.10.1 bundle and unauthenticated runs in the dev container. Any non-empty `BW_CLEANEXIT` turns a failure into exit code 0. Prompts go to standard error, and only `BW_NOINTERACTION=true` stops the unlock prompt. The login ignores a failed sync. A fresh profile contacts Bitwarden Cloud on its first start, also before a server is set. `bw logout` does not remove the device on the server. Mostly code-level evidence; the login from a Go parent, Bitwarden Cloud with an account and the premium failure were not tested. |
| Archive and trash filters | [Code notes of 16 November 2026](bw-cli-code-notes-2026-11-16.md) on the 2026.10.1 bundle. `bw list items` leaves archived and deleted items out, `--archived` returns only archived items, and for an account without premium from any source `--archived` is dropped without an error, so the default list is returned again. Both personal exports leave deleted items out, so the trash is in no captured document. Code reading only; an account that may not archive, the trash and an archived item with an attachment were not observed live. |
| Sync behavior of list, export and get | [Code notes of 17 November 2026](bw-cli-code-notes-2026-11-17.md) on the 2026.10.1 bundle. `bw list items`, both personal exports and `bw get attachment` read the local snapshot and start no sync. Every `fullSync` call lies in login, unlock, `sync`, import, the organization API service and the account migrations. The migrations run only from login and unlock, which `BW_NOINTERACTION=true` keeps out of other commands, and the CLI starts no timer or notification handler that syncs. One forced sync therefore fixes the snapshot for every later document. Code reading only; no network trace was taken. |
| Login from a Go parent | [Manual exercise of 15 November 2026](login-exercise-2026-11-15.md) with `internal/tools/loginprobe` against Vaultwarden 1.37.4, one synthetic account with TOTP, on Linux arm64 (npm `bw`, five cases) and macOS arm64 (single-file `bw`, three cases). The login works without a pseudo-terminal on both. Ctrl-C at the password prompt reached no signal to the parent: `bw` ended with exit code 0 and no session key, and the key form check failed the login; the terminal echoed again. After the logout `data.json` still held 12 `user_` entries. Each successful login left one device entry on the server. Bitwarden Cloud, Windows and a vault with items were not tested. |
| Account registration without a person | [Spike of 21 November 2026](vaultwarden-registration-spike-2026-11-21.md) against Vaultwarden 1.37.4 on Linux arm64. Two HTTP calls registered a synthetic account with keys derived in test code (PBKDF2-SHA256, 600 000 iterations); both returned 200. bw 2026.10.1 logged in with `--passwordenv`, unlocked, synced and seeded a login with a passkey, two logins with attachments and one archived item: the default list showed 2 items, the archived list 1, the plaintext export 3 with 1 passkey, all in the legacy format. Vaultwarden reports premium for every user (code reading). The amd64 binary was hashed, not run; a pseudo-terminal, the product, tampering and Bitwarden Cloud were not tested. |
| Organization roles and exports | [Spike of 21 November 2026](organization-export-spike-2026-11-21.md) against Vaultwarden 1.37.4 on Linux arm64 with bw 2026.10.1, one organization with two collections and synthetic owner, admin, user and manager accounts. An admin assigned to one collection saw the items of both and downloaded both attachments. Owner and admin exported the organization in both formats with the same IDs and `revisionDate` as `bw list items`; both exports left out the trash item. For a user and a manager the export got 401 and `bw` logged out. `bw list organizations` reported owner 0, admin 1, user 2, the manager as 4, and confirmed as status 2. Code reading: the organization export is a server read on every call, exports the whole organization and checks no permission in the client. Bitwarden Cloud, custom roles, blob items, passkeys, decryption error lines and a change during a run were not tested. |
