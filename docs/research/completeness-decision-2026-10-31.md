# Bitwarden CLI 2026.10.1 · Kann ein erfolgreicher Export fehlende Passkeys erkennen?

**No-Go für die unveränderte CLI als Backend mit Vollständigkeitszusage.** Für einen persönlichen Vault liefert sie aber einen brauchbaren zweiten Messpunkt. Der kontogebundene Export mit `bw export --format encrypted_json` ohne `--password` verarbeitet verschlüsselte Items vor der Entschlüsselung. In unserem Legacy-Test enthielt er zwei Credential-Einträge, während der normale JSON-Export für denselben Login keinen einzigen enthielt. Für Blob-Items liefert derselbe Messpunkt nur die äußere Item-ID. Die Anzahl der versiegelten Passkeys bleibt unbekannt.

**Bedingtes Go für Ansatz B als Upstream-Prototyp.** Das gepinnte SDK kann den getesteten Schaden bereits erkennen. Die CLI müsste diese Erkenntnis bis zum Aufrufer transportieren und auch den Schritt von entschlüsselten Views zu JSON prüfen. Eine Vollständigkeitszusage braucht einen benannten Bezugspunkt, etwa „alle exportberechtigten persönlichen Items im fixierten lokalen Snapshot“. Für „alle auf dem Server vorhandenen Items“ reicht auch ein strenger lokaler Export allein nicht aus.

## Was tatsächlich lief

Der vorhandene saubere offizielle Clients-Checkout hatte HEAD `91214c3b978edb5496a32a946451960fe7d44531`. CLI-Paketversion und beide SDK-Abhängigkeiten wurden im Checkout gelesen. Das öffentliche npm-Paket wurde frisch heruntergeladen und sein SHA-512 mit den archivierten npm-Metadaten verglichen. Diese ordnen ihm SDK-Commit `4a9eb239fa7f63132ad7a32cce9aeb5fae252243` zu. Geprüft wurden die lokalen Rust-Quelldateien aus dem Audit sowie das ausführbare öffentliche Node/WASM-Paket. Der kommerzielle Build wurde nicht ausgeführt. [CLI-Version](https://github.com/bitwarden/clients/blob/91214c3b978edb5496a32a946451960fe7d44531/apps/cli/package.json#L4) · [SDK-Pins](https://github.com/bitwarden/clients/blob/91214c3b978edb5496a32a946451960fe7d44531/package.json#L188) · [npm-Metadaten](https://registry.npmjs.org/@bitwarden%2Fsdk-internal/0.2.0-main.1126)

Der SDK-Test erzeugt ausschließlich lokale, flüchtige Testschlüssel mit Bitwardens eigener Kryptografie. Er verschlüsselt einen Login mit zwei synthetischen Credentials. In einer Kopie ersetzt er nur das zweite verschlüsselte `keyValue` durch einen syntaktisch gültigen, unter einem fremden Schlüssel erzeugten EncString. In einer weiteren Kopie ersetzt er den gewrappten Itemschlüssel. Die Schlüsselwerte im Credential-Klartext sind Teststrings. Geprüft wird der Verlust beim Entschlüsseln und Serialisieren, keine WebAuthn-Anmeldung.

| Eingabe | SDK-Modus | Erfolgreiche Items / Itemfehler | Passkeys im JSON | Abgleich mit verschlüsselter Quelle |
|---|---|---:|---:|---|
| Intakt, zwei Passkeys | tolerant und strict | 1 / 0 | 2 | Anzahl stimmt |
| Zweites keyValue defekt | tolerant | **1 / 0** | **0** | 2 erwartet, 0 erhalten |
| Zweites keyValue defekt | strict | 0 / 1 | Item fehlt | ID fehlt |
| Itemschlüssel defekt | tolerant und strict | 0 / 1 | Item fehlt | ID fehlt |

Ausgeführt wurden `decrypt_list_full_with_failures` des offiziellen WASM-Pakets, anschließend die Originalmethoden des persönlichen JSON- und encrypted_json-Exporters. Der Test übergibt die SDK-Erfolge direkt an die Servicegrenze und die verschlüsselten Eingaben an den Inventarpfad. Originale Exportmapper laufen mit, Netzwerk, Storage, DI, Policy und die Schlüsselvalidierung des Exportcontainers sind Testdoubles. Das ist eine Reproduktion des False Success auf SDK- und Exportservice-Ebene. Kein authentifizierter CLI-Prozess, kein simuliertes Prozess-Exit-Ergebnis, kein Restore und kein produktives Profil wurden verwendet. Die CLI benutzt im SDK-CRUD-Pfad `get_all()` auf dem Repository. Dieser Nachbarpfad wurde im Quellcode geprüft. [SDK-Brücke](https://github.com/bitwarden/clients/blob/91214c3b978edb5496a32a946451960fe7d44531/libs/common/src/vault/services/cipher-sdk.service.ts#L460) · [SDK-Repositorypfad](https://github.com/bitwarden/sdk-internal/blob/4a9eb239fa7f63132ad7a32cce9aeb5fae252243/crates/bitwarden-vault/src/cipher/cipher_client/get.rs#L65)

**Weitere ausgeführte Grenztests.** Eine modellierte Auslassung nur eines von zwei Credentials erzeugte eine Anzahlabweichung. Ein Credential ohne Schlüsselwert erzeugte eine Pflichtfeldverletzung. Ein anderes Credential bei gleicher Anzahl blieb unentdeckt. Ein synthetischer Blob-Umschlag durchlief den echten Exportmapper und ergab „Anzahl unbekannt“. Sein Inhalt wurde nicht kryptografisch geöffnet. Ein simuliertes `fullSync(false-Ergebnis)` ergab im echten SyncCommand eine Erfolgsmeldung. Mit einem von zwei simulierten Serveritems im lokalen Bestand stimmten beide Exporte überein. Nur die getrennt gespeicherte erwartete Server-ID-Menge erkannte die Lücke. Das modelliert einen unvollständigen Sync und beweist keinen konkreten serverseitigen Verlust im Release.

## A · Was das verschlüsselte Inventar leisten kann

Für persönliche Daten verwendet der kontogebundene encrypted_json-Pfad `getAll`, der JSON-Pfad `getAllDecrypted`. Beim passwortgeschützten Export wird zuerst normales JSON erzeugt. Dieser Weg erbt dessen Auslassungen. Auch `bw list items` verwendet die entschlüsselte Sicht. Der kontogebundene Pfad ist damit unabhängig **vom Decrypt-Schritt**, teilt aber Sync-Quelle, Scope-Filter und Teile der Exportmapper. Eine Auslassung im gemeinsamen Mapper kann beide Seiten treffen. [Verschlüsselter Inventarpfad](https://github.com/bitwarden/clients/blob/91214c3b978edb5496a32a946451960fe7d44531/libs/tools/export-vault-core/src/services/individual-vault-export.service.ts#L245) · [Passwortgeschützter Export](https://github.com/bitwarden/clients/blob/91214c3b978edb5496a32a946451960fe7d44531/libs/tools/export-vault-core/src/services/individual-vault-export.service.ts#L73) · [List](https://github.com/bitwarden/clients/blob/91214c3b978edb5496a32a946451960fe7d44531/apps/cli/src/commands/list.command.ts#L70)

Im lokalen Benutzerzustand existiert ein `CIPHERS_DISK`-Record aus verschlüsselten `CipherData`. Die CLI speichert ihren Zustand mit LowDB in `data.json`. Das SDK verwendet einen Mapper für denselben Record. Äußere IDs, Typ, Berechtigungen, Datumsfelder und Attachment-Metadaten sind nach dem Modellvertrag lesbar. **Eine unterstützte Passkey-Anzahl gibt es unter diesen Metadaten nicht.** Im Legacy-Format lässt sich die Länge eines tatsächlich vorhandenen `login.fido2Credentials`-Arrays technisch ablesen. Bitwarden weist ausdrücklich darauf hin, dass diese per Feld verschlüsselten inneren Eigenschaften außerhalb der Verschlüsselungsschicht nicht als stabile Schnittstelle gelesen werden sollen. Daraus folgt keine Berechtigungsaussage über fremde Vaults. Der öffentliche encrypted_json-Pfad ist für A dem direkten Profilparser vorzuziehen. [State](https://github.com/bitwarden/clients/blob/91214c3b978edb5496a32a946451960fe7d44531/libs/common/src/vault/services/key-state/ciphers.state.ts#L17) · [LowDB](https://github.com/bitwarden/clients/blob/91214c3b978edb5496a32a946451960fe7d44531/apps/cli/src/platform/services/lowdb-storage.service.ts#L59) · [SDK-State](https://github.com/bitwarden/clients/blob/91214c3b978edb5496a32a946451960fe7d44531/libs/common/src/vault/models/domain/cipher-sdk-mapper.ts#L10) · [Modellvertrag](https://github.com/bitwarden/clients/blob/91214c3b978edb5496a32a946451960fe7d44531/libs/common/src/vault/models/domain/cipher.ts#L32)

Bei Blob-Verschlüsselung liegen Login und Passkeys im versiegelten `data`-Umschlag. Der Exporter erkennt beim Domainobjekt die Zeichenfolge `"format_version"` und übernimmt den Umschlag. Sein Upstream-Test zeigt Version 1 mit `wrapped_cek` und `envelope`. Auch Legacy-Rohdaten können ein `data`-Feld tragen. Eine bloße Prüfung auf Feldexistenz klassifiziert das Rohprofil daher falsch. Die Upstream-Erkennung ist ein Implementierungsdetail. Unbekannte, widersprüchliche oder gemischte Formen müssen je Item zu „unverifiziert“ führen. Eine fehlende Login-Struktur im Blob bedeutet niemals „null Passkeys“. PAM-Partial-Daten bilden einen weiteren Sonderfall mit vorenthaltenen Geheimnissen. [Exporter und Marker](https://github.com/bitwarden/clients/blob/91214c3b978edb5496a32a946451960fe7d44531/libs/common/src/models/export/cipher.export.ts#L251) · [Legacy- und Blob-Beispiele](https://github.com/bitwarden/clients/blob/91214c3b978edb5496a32a946451960fe7d44531/libs/common/src/models/export/cipher.export.spec.ts#L48) · [SDK-Dispatch](https://github.com/bitwarden/sdk-internal/blob/4a9eb239fa7f63132ad7a32cce9aeb5fae252243/crates/bitwarden-vault/src/cipher/cipher.rs#L1651)

Für A sind ID-Mengen mit Eindeutigkeitsprüfung und Passkey-Anzahlen **pro Item** sinnvoll. Leere Pflichtfelder sind ein überprüfbarer Defekt. Eine gleiche Anzahl beweist weder Credential-Identität noch einen korrekten Schlüsselinhalt. Zwei separat gestartete CLI-Befehle können unterschiedliche Revisionen sehen. Konto, Filter, Löschstatus, Rechte und Snapshot müssen vergleichbar sein. Der persönliche Export schließt Organisationsitems aus. Die Organisationsexporte haben eigene Pfade für verwaltete Collections und den organisatorischen Exportendpunkt. Die persönlichen Testergebnisse gelten für diese Pfade nicht automatisch. [Persönliche Filter](https://github.com/bitwarden/clients/blob/91214c3b978edb5496a32a946451960fe7d44531/libs/tools/export-vault-core/src/services/individual-vault-export.service.ts#L211) · [Organisation](https://github.com/bitwarden/clients/blob/91214c3b978edb5496a32a946451960fe7d44531/libs/tools/export-vault-core/src/services/org-vault-export.service.ts#L109)

## B · Minimaler upstream-freundlicher Änderungsvorschlag

1. Einen opt-in Modus für persönlichen JSON-Export vorsehen, beispielsweise `bw export --format json --strict`. Am SDK-Einstieg für genau diesen Aufruf strikte **vollständige** Entschlüsselung anfordern. Keine ListView verwenden, denn sie entschlüsselt `keyValue` nicht. Keine früheren toleranten Views übernehmen. Das bestehende Feature-Flag hat clientseitig Default FALSE. Ein globales Umschalten wäre bei gleichzeitigen Aufrufen kein verlässlicher Vertrag. Falls das SDK nur das Flag anbietet, einen pro Aufruf wählbaren Modus ergänzen. [Login-FullView und ListView](https://github.com/bitwarden/sdk-internal/blob/4a9eb239fa7f63132ad7a32cce9aeb5fae252243/crates/bitwarden-vault/src/cipher/login.rs#L567) · [Strikte und tolerante Arraybehandlung](https://github.com/bitwarden/sdk-internal/blob/4a9eb239fa7f63132ad7a32cce9aeb5fae252243/crates/bitwarden-vault/src/cipher/login.rs#L487) · [Flag](https://github.com/bitwarden/clients/blob/91214c3b978edb5496a32a946451960fe7d44531/libs/common/src/enums/feature-flag.enum.ts#L177)
2. Für **denselben** fixierten Eingabebestand in einem Aufruf Erfolge, Fehler und dokumentierte Scope-Ausschlüsse zurückgeben. Jede erwartete ID muss genau einmal bilanziert sein. Exceptions, fehlende Ergebnisse oder nicht konvertierbare Views müssen den Export stoppen. Der heutige Service speichert Fehler separat, reicht nur Erfolge weiter und kann Exceptions in ein leeres Array übersetzen. Das nachträgliche Lesen eines Fehler-Observables reicht wegen Cache, Timing und früher verschluckter Feldfehler nicht. [Service](https://github.com/bitwarden/clients/blob/91214c3b978edb5496a32a946451960fe7d44531/libs/common/src/vault/services/cipher.service.ts#L375) · [Brücke mit View-Filter](https://github.com/bitwarden/clients/blob/91214c3b978edb5496a32a946451960fe7d44531/libs/common/src/vault/services/cipher-sdk.service.ts#L670)
3. Vor Veröffentlichung des JSON das Ergebnis pro Item mit der **strikten FullView** vergleichen. Gefordert sind dieselben Credentials und die versionsgerecht serialisierten Werte aller Felder einschließlich `keyValue` und optionaler Felder. Der Vergleich erfolgt im Speicher, ohne Geheimnisse im Fehlerbericht. Er prüft die Serialisierung auch bei Blob-Eingaben. Er liefert dort keine zweite unabhängige Zählung des versiegelten Inhalts. Bei explizit geforderter unabhängiger Passkey-Zahl bleibt ein solcher Lauf unverifiziert. [FIDO2-Mapper](https://github.com/bitwarden/clients/blob/91214c3b978edb5496a32a946451960fe7d44531/libs/common/src/models/export/fido2-credential.export.ts#L118)
4. Erst nach erfolgreicher Prüfung schreiben. Für Fehler genügt ein stabiler maschinenlesbarer Grund wie `decrypt_failed`, `scope_unknown` oder `export_mismatch`, mit aggregierten Zählern auf stderr. Exit 0 nur bei erfülltem vereinbartem Prüfvertrag. Heute kann bereits ein gesetztes `BW_CLEANEXIT` eine Fehlerantwort in Exit 0 umwandeln. Strict braucht eine explizite Ausnahme oder muss diese Kombination vorab mit wirksamem Fehlercode zurückweisen. Quiet/Raw dürfen den Code nicht verändern. [Prozessantwort](https://github.com/bitwarden/clients/blob/91214c3b978edb5496a32a946451960fe7d44531/apps/cli/src/base-program.ts#L24)

**PR-Abnahmetests, noch offen.** Die sechs ausgeführten SDK-Fälle zusätzlich über den echten CLI-Prozesseinstieg prüfen, einschließlich bestehendem toleranten Cache, deaktiviertem Flag, geworfener SDK-Exception und Mapper-Verlust bei gleicher Anzahl. Erwartet werden Fehlercode, kein Erfolg auf stdout und keine neue oder überschriebene Zieldatei. Dazu intakter leerer Snapshot versus fehlender State, Legacy und gültiger Blob im selben Bestand, Partial-/Org-Scope, unbekannte Version und Sync-Wechsel während des Exports. Je Fall mit und ohne `BW_CLEANEXIT` testen. Der vorgeschlagene Schalter ist weder implementiert noch als PR eingereicht.

## C · SDK-Adapter als Rückfalloption

Der WASM-Test belegt den technischen Zugriff auf strikte volle Ergebnisse. Ein Adapter müsste zusätzlich State, Schlüsselkontext, Scope, Snapshot und Mapper-Verträge pflegen. Das Paket bezeichnet sich als intern und ohne Support. Er löst die fehlende serverseitige Referenz genauso wenig wie B. C kommt erst infrage, wenn B upstream ausscheidet und der eng gepinnte Adapter seine Testmatrix pro Release besteht. Es ist keine eigene Kryptografie erforderlich.

## Freigaberegeln und Restrisiken

| Meldung | Entscheidung |
|---|---|
| **Fehlgeschlagen** | Expliziter Sync-/Decrypt-/Mapperfehler, fehlende Pflichtdaten, doppelte ID oder nachgewiesene Abweichung bei identischem Scope und Snapshot. Ein Fehler genügt, auch wenn weitere Items unverifizierbar sind. |
| **Unverifiziert** | Export vorhanden, mindestens ein wesentlicher Nachweis fehlt. Beispiele sind ein nicht vergleichbarer Snapshot, nur lokal bekannte IDs bei beanspruchter Serverabdeckung, ein unbekanntes Schema oder ein Blob bei geforderter unabhängiger Credential-Anzahl. |
| **Verifiziert** | Nur für den angegebenen Umfang und Bezugspunkt. Für das hier verlangte unabhängige Vollständigkeitsversprechen müssen erwartete IDs und Credential-Bestand unabhängig feststehen, alle Fehler ausgeschlossen und die vollständige Serialisierung geprüft sein. Im Test kennt die Fixture diese Sollwerte. Die unveränderte CLI liefert sie im allgemeinen Einsatz nicht. |

Ein Zeitstempel oder erfolgreicher Sync-Aufruf zertifiziert keine Server-ID-Menge. `fullSync` kann auch ohne erforderliches Update false liefern, weshalb false allein keinen Datenverlust beweist. Für die Zusage eines frischen Snapshots braucht es ein bestätigtes Ergebnis mit eindeutiger Semantik. Für serverweite Vollständigkeit wäre zusätzlich eine autoritative, revisionsgebundene Inventarliste desselben berechtigten Scopes nötig. Ein solcher öffentlicher persönlicher CLI-Kanal wurde hier nicht belegt. Ein historisches Manifest kann Änderungen melden, aber allein keine legitime Löschung von einem fehlenden Sync-Item unterscheiden. [Sync-Service](https://github.com/bitwarden/clients/blob/91214c3b978edb5496a32a946451960fe7d44531/libs/common/src/platform/sync/default-sync.service.ts#L130) · [CLI-Sync](https://github.com/bitwarden/clients/blob/91214c3b978edb5496a32a946451960fe7d44531/apps/cli/src/vault/sync.command.ts#L19)

Restrisiken sind unbekannte Abbildungsverluste innerhalb des SDK, Änderungen am Scope und zukünftige Feld- oder Blob-Versionen. Ein erfolgreich entschlüsselter, aber bereits in der Quelle falscher Schlüssel bleibt außerhalb der Vollständigkeitsprüfung. Für jedes Upgrade Clients-SHA, SDK-Paketintegrität, Buildvariante, Mapper und Feature-Flags festhalten und dieselben positiven und negativen Fixtures erneut ausführen. Unbekannte Kombinationen erhalten keine automatische Freigabe. Anhänge, Restore und die Bereitstellung eines Backup-Tools waren außerhalb dieser Untersuchung.

## Reproduktion

Node 26.13.0, TypeScript 5.9.3, RxJS 7.8.2, JSZip 3.10.1. Beide CJS-Dateien gemeinsam in ein leeres Arbeitsverzeichnis legen. Die Kommandos beziehen nur öffentliche Pakete und Quellcode. Die Tests selbst benötigen kein Netzwerk, keine CLI-Anmeldung und kein Vault-Profil.

```sh
git clone https://github.com/bitwarden/clients.git clients
git -C clients checkout --detach 91214c3b978edb5496a32a946451960fe7d44531
npm install --no-save typescript@5.9.3 rxjs@7.8.2 jszip@3.10.1
npm pack @bitwarden/sdk-internal@0.2.0-main.1126
openssl dgst -sha512 -binary bitwarden-sdk-internal-0.2.0-main.1126.tgz | openssl base64 -A
tar -xzf bitwarden-sdk-internal-0.2.0-main.1126.tgz
node inventar-test.cjs clients
node sdk-test.cjs clients package
```
